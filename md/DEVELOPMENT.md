# راهنمای توسعه

## پیش‌نیاز و راه‌اندازی

Node.js شاخه ۲۴ و npm شاخه ۱۱ مطابق engines در package.json لازم‌اند. مدیر بسته فقط npm است؛ package-lock.json حذف یا با lockfile دیگری جایگزین نشود.

```bash
npm ci
npm run dev
```

پیش از اجرای سرور، env محلی را مطابق [اتصال دیتابیس](#اتصال-دیتابیس) تنظیم و `npm run db:generate` را اجرا کنید؛ generated/prisma در Git نیست و پس از clone باید تولید شود. نمونه env فقط برای راه‌اندازی است و نباید روی فایل خصوصی موجود بازنویسی شود.

سرور توسعه معمولاً روی پورت 3000 اجرا می‌شود؛ اگر پورت در استفاده باشد، آدرس خروجی Next.js ملاک است. اطلاعات نسخه‌ها و تصمیم‌های وابستگی در [TECH_STACK.md](TECH_STACK.md) و وضعیت سرویس‌ها در [ARCHITECTURE.md](ARCHITECTURE.md) است.

## استقرار روی Vercel

مخزن GitHub را در Vercel با Add New → Project وارد کنید. Framework را Next.js، Root Directory را ریشه مخزن، Node.js را 24.x، Install Command را `npm ci` و Build Command را `npm run build -- --webpack` بگذارید. Output Directory پیش‌فرض Next.js باقی بماند. Webpack فعلاً مسیر بیلد تأییدشده این پروژه است.

در Environment Variables محیط Production، این مقادیر را به‌صورت خصوصی تنظیم کنید:

| متغیر                 | مقدار                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL`        | اتصال pooler موجود با رمز percent-encoded، `sslmode=verify-full` و `sslrootcert=certs/supabase-prod-ca-2021.crt`؛ مسیر نسبی Linux باشد، نه مسیر ویندوز |
| `NEXTAUTH_SECRET`     | secret تصادفی مخصوص production با دست‌کم ۳۲ نویسه                                                                                                      |
| `NEXTAUTH_URL`        | مبدأ HTTPS دامنه نهایی برنامه، بدون مسیر اضافی                                                                                                         |
| `SUPABASE_URL`        | آدرس HTTPS پروژهٔ Storage                                                                                                                              |
| `SUPABASE_SECRET_KEY` | کلید خصوصی سرور برای عکس دسته‌بندی؛ هرگز با پیشوند `NEXT_PUBLIC_` تعریف نشود                                                                           |

گواهی عمومی با `outputFileTracingIncludes` در `next.config.ts` به trace خروجی سرور اضافه می‌شود، چون مسیر آن از env خوانده می‌شود و قابل کشف ایستا نیست. هیچ‌یک از متغیرهای بالا پیشوند NEXT_PUBLIC_ ندارند. فایل env محلی و متغیرهای OWNER را آپلود نکنید؛ حساب مالک قبلاً در دیتابیس ساخته شده است. `DIRECT_URL` برای runtime لازم نیست و migration یا ساخت مالک را به Build Command اضافه نکنید.

پس از تعیین دامنه، `NEXTAUTH_URL` را با آن تطبیق دهید؛ تغییر env نیاز به Redeploy دارد. برای Preview از دیتابیس آزمایشی و secret مستقل استفاده کنید؛ اتصال Preview به دیتابیس اصلی را خودکار فعال نکنید. پس از استقرار، صفحه اصلی، تغییر زبان و تم، ورود، نشست و خروج را روی دامنه HTTPS بررسی کنید. بیلد محلی موفق جای بررسی اتصال دیتابیس در runtime Vercel را نمی‌گیرد.

مراجع رسمی: [Node.js در Vercel](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions) و [مدیریت متغیرهای محیطی](https://vercel.com/docs/environment-variables/managing-environment-variables).

## دستورهای روزمره

### حساب آزمایشی پنل

حساب `test@gmail.com` برای آزمون دستی ورود و مدیریت محصولات معرفی شده است. رمز از اطلاعات خصوصی ارائه‌شده توسط مالک پروژه دریافت می‌شود و در مستندات یا کد مخزن ثبت نمی‌شود. نقش و فعال‌بودن حساب هنگام آزمون بررسی شوند؛ داده‌های آزمایشی محصول با وضعیت پیش‌نویس ساخته شوند.

### بررسی مدیریت محصولات

بازبینی اسکلتون فهرست دسته‌بندی در ۲۰۲۶/۱۱/۲۴: حالت dev در فارسی/انگلیسی و روشن/تیره مشاهده و بازگشت به محتوای واقعی تأیید شد. در نمونهٔ پنج‌ردیفی، ارتفاع tbody پیش و پس از اسکلتون ۴۰۴px و تعداد ردیف‌ها ۵ باقی ماند. این نتیجه مربوط به دادهٔ نمونهٔ جاری است؛ loading اولیه تعداد نتیجه را از پیش نمی‌داند. سه طرح برداری بدون عکس با لوگوی موجود و نسخه‌های روشن/تیره تولید و تصویری بررسی شدند؛ جایگزینی فعال به انتخاب مالک موکول است.

پس از این تغییر، `npm run check` با ۱۳۶ تست در ۱۸ فایل و بیلد production Webpack موفق بودند.

بازبینی نام اختصاصی در ۲۰۲۶/۱۱/۲۴: ساخت خودکار از نام انگلیسی و حفظ مقدار دستی پس از تغییر دوبارهٔ نام انگلیسی در فرم محصول و دسته‌بندی بررسی شد. ارسال دسته‌بندی با نام اختصاصی موجود، خطای تکراری داد و رکورد جدید نساخت. خطای soft در فارسی/انگلیسی و دو تم بررسی شد؛ اندازهٔ محاسبه‌شدهٔ متن و آیکون هر دو ۱۴px بود. جدول دسته‌بندی نام جاری را تنها به زبان صفحه نمایش می‌دهد. فیلدهای ضروری با ستاره مشخص‌اند؛ قرارداد در سیستم طراحی و منطق نام اختصاصی در معماری ثبت است.

`npm run check` در این بازبینی با ۱۳۶ تست در ۱۸ فایل موفق بود؛ دو تست تازه تبدیل نام انگلیسی، کاراکترها و سقف نام اختصاصی را پوشش می‌دهند.

#### عکس دسته‌بندی

بازبینی اسکلتون و تصویر بدون عکس در ۲۰۲۶/۱۱/۲۴: فرم ساخت/ویرایش به `CategoryEditorSkeleton` و `new/loading.tsx` وصل شد. سوییچ dev، اسکلتون و بازگشت به فرم را در فارسی/انگلیسی و هر دو تم نشان داد. جای ورودی‌ها، عکس و دکمه‌ها با فرم هماهنگ است. تصویر دانلودشدهٔ `public/images/no-image.png` در فرم و ردیف‌های بدون عکس جدول مشاهده شد و `complete/naturalWidth` بارگذاری محلی آن را تأیید کرد. `npm run check` با ۱۳۶ تست در ۱۸ فایل موفق بود. منبع و مشخصات فایل در معماری ثبت شده است.

بیلد production با `npm run build -- --webpack` پس از افزودن loading فرم و تصویر محلی موفق بود.

بازبینی کامپوننت مشترک در ۲۰۲۶/۱۱/۲۴: اکانت و دسته‌بندی از `ImageEditor` و `ImagePreview` استفاده می‌کنند. مودال، حالت بدون عکس و دکمه‌های مشترک در فارسی/انگلیسی و دو تم در هر دو صفحه بررسی شدند. انتخاب فایل واقعی از مودال مشترک، نمایش برش، تغییر زوم، تأیید مودال و ذخیرهٔ اصلی دسته‌بندی تا بازگشت به فهرست موفق بود. عکس ذخیره‌شده پس از ورود مجدد به ویرایش نمایش داده شد؛ حذف و لغو حذف هم بررسی شدند. محدودیت انتخاب‌گر داخلی که در آزمون قبلی ثبت شده بود، در این آزمون تکرار نشد. اطلاعات حساب آزمایشی در این بازبینی تغییر نکرد.

پس از استخراج کامپوننت مشترک، `npm run check` با ۱۳۴ تست در ۱۷ فایل و `npm run build -- --webpack` موفق بودند.

در ۲۰۲۶/۱۱/۲۳ migration هفتم ستون nullable `Category.imagePath` را اضافه کرد و روی دیتابیس اعمال شد؛ `db:migrate:status` همگام‌بودن را تأیید کرد. در ۲۰۲۶/۱۱/۲۴ مالک کلید خصوصی را در `.env.local` تنظیم کرد و آپلود و بازخوانی واقعی Storage موفق بود. فرم بدون عکس به کلید Storage نیاز ندارد. در استقرار هم کلید موجود پروژه فقط در env خصوصی میزبان با نام `SUPABASE_SECRET_KEY` قرار گیرد؛ کلید قدیمی `SUPABASE_SERVICE_ROLE_KEY` نیز پشتیبانی می‌شود. مرجع [API Keys](https://supabase.com/docs/guides/api/api-keys) است. کلید در Git، چت و MD ثبت نشود.

آپلود فرم multipart است. محدودیت Server Action برابر ۳MB است تا فایل مجاز ۲MB و سربار فرم جا شوند. Sharp فقط JPEG/PNG/WebP تک‌فریم، حداکثر ۱۶ میلیون پیکسل را قبول می‌کند. کلید فایل تصادفی و فرمت نهایی WebP است؛ فایل خام در Storage ذخیره نمی‌شود. bucket خصوصی در اولین آپلود معتبر ساخته می‌شود.

`npm run check` با ۱۳۴ تست در ۱۷ فایل و بیلد Webpack پس از افزودن عکس موفق بودند. تست‌ها نوع واقعی فایل، سقف حجم/پیکسل، تبدیل WebP، مجوز، حفظ عکس قبلی، تعویض و حذف، تداخل و جبران شکست دیتابیس را پوشش می‌دهند؛ مسیر دریافت عکس نیز تست مجوز و عدم cache عمومی دارد.

آزمون یکپارچهٔ واقعی در ۲۰۲۶/۱۱/۲۴ با ورود حساب آزمایشی و درخواست multipart به Server Action انجام شد: ایجاد دسته‌بندی با عکس، ثبت مسیر در دیتابیس، پاسخ WebP با `private, no-store`، تعویض عکس و پاک‌شدن فایل قبلی، حذف عکس و پاسخ ۴۰۴، آپلود مجدد، خصوصی‌بودن bucket و رد دسترسی عمومی همگی موفق بودند. «دسته‌بندی تست عکس / Image Test Category» با نامک `category-image-check-20261124` و یک عکس نمونه برای بازبینی باقی ماند. انتخاب‌گر فایل ابزار مرورگر داخلی پاسخ نداد؛ ارسال multipart از HTTP انجام شد و کلیک انتخاب فایل آزمون موفق محسوب نمی‌شود.

در مرورگر، عکس جدول و پیش‌نمایش ویرایش در فارسی و انگلیسی و هر دو تم روشن/تیره مشاهده شد. تغییر زبان شناسهٔ ویرایش را حفظ کرد. تأیید فرم انگلیسی با حفظ عکس قبلی به فهرست برگشت؛ حذف عکس و سپس انصراف در فرم فارسی، عکس ذخیره‌شده را حفظ کرد. رفتار انتخاب فایل بومی Chrome در این نوبت به‌دلیل محدودیت ابزار پنجرهٔ کوچک‌شده بررسی نشد.

بازنگری عملیات دسته‌بندی در ۲۰۲۶/۱۱/۲۳: `npm run check` با ۱۱۶ تست در ۱۴ فایل و بیلد نهایی Webpack موفق بودند. تست‌های جدید مجوز ADMIN/OWNER، رد مهمان/مشتری، اعتبارسنجی، تداخل ویرایش، نامک تکراری، حذف مشروط به نداشتن محصول و خطای کلید خارجی هنگام افزودن هم‌زمان محصول را پوشش می‌دهند. در مرورگر، فرم ویرایش پرشده، ذخیرهٔ بدون تغییر مقادیر حساب آزمایشی و بازگشت به فهرست، بازشدن تأیید حذف و انصراف از آن بررسی شد؛ دسته‌بندی واقعی حذف نشد. شمارندهٔ نتایج به ابتدای صفحه‌بندی مشترک منتقل شده و سلول‌های دسته‌بندی وسط‌چین‌اند. قرارداد جاری در [سیستم طراحی، صفحه‌بندی مشترک](DESIGN_SYSTEM.md#صفحه‌بندی-مشترک) ثبت شده است.

بازنگری جدول و دسته‌بندی در ۲۰۲۶/۱۱/۲۳: جدول مشترک `components/ui/table.tsx` در کاربران، محصولات و دسته‌بندی‌ها به کار رفت. دکمهٔ ساخت گرادیانی کنار تیتر دسته‌بندی به `/[locale]/admin/categories/new` می‌رود؛ فرم ساخت و پیوند بازگشت به محصولات از فهرست حذف شدند. `npm run check` با ۱۰۶ تست موفق بود. بیلد Webpack پیش از اصلاحات نهایی تراز سلول، شکستن متن سرستون و عرض جست‌وجوی موبایل موفق شد؛ پس از این اصلاحات check دوباره موفق بود.

فهرست و فرم ساخت دسته‌بندی در فارسی/انگلیسی و روشن/تیره در مرورگر بررسی شدند. جدول کاربران و سوییچ اسکلتون آن و جدول محصولات نیز پس از استخراج جزء مشترک بررسی شدند. در عرض ۳۹۰ پیکسل، اسکرول افقی RTL دسته‌بندی از صفر به منفی ۳۲۵ پیکسل رسید و مختصات ستون اول ثابت ماند. اندازهٔ مرورگر پس از آزمون به حالت قبل برگشت. این بررسی جای آزمون گوشی فیزیکی یا audit کامل دسترس‌پذیری نیست.

بازنگری مسیرها در ۲۰۲۶/۱۱/۲۳: دسته‌بندی‌ها، ساخت محصول و ویرایش محصول به صفحات مستقل منتقل شدند. `npm run check` با ۱۰۶ تست و بیلد `npm run build -- --webpack` موفق بودند. ذخیرهٔ همان محصول آزمایشی در صفحهٔ مستقل و بازگشت به فهرست در مرورگر تأیید شد.

در ۲۰۲۶/۱۱/۲۳، `npm run check` با ۱۰۶ تست موفق شد و بیلد Webpack پس از اصلاح ترجمهٔ حالت بارگذاری موفق بود. اسکلتون محصولات مانند اجزای دیگر پنل از Provider ترجمهٔ سمت کلاینت استفاده می‌کند.

در مرورگر داخلی، ورود حساب آزمایشی با نقش ADMIN، ساخت دسته‌بندی «لوازم جانبی آزمایشی» (`test-accessories`) و ساخت محصول پیش‌نویس «هدفون آزمایشی تک‌شاپ» (`tech-shop-test-headphones`) تأیید شد. محصول یک تنوع مشکی با کد `TEST-HEADPHONES-BLACK`، قیمت ۲۵٬۰۰۰٬۰۰۰ ریال و موجودی ۵ دارد. این داده‌ها برای ادامهٔ آزمون نگه داشته شده‌اند. بازگشایی فرم، نام‌ها و توضیحات دوزبانه و مقادیر ذخیره‌شده را نشان داد. فهرست در فارسی/انگلیسی و روشن/تیره بررسی شد؛ این بررسی سنجش عملکرد یا audit کامل دسترس‌پذیری نیست.

## قواعد تغییرات

- پیش از تغییر API یا قرارداد Next.js، راهنمای مرتبط در node_modules/next/dist/docs خوانده شود؛ به دانش نسخه‌های قبلی اکتفا نشود.
- Tailwind روش اصلی استایل‌نویسی و daisyUI مرجع اجزا و تم است؛ جزئیات در [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md).
- نسخه‌های مستقیم پایدار و سازگار انتخاب شوند. beta/RC، force و legacy-peer-deps برای دورزدن ناسازگاری استفاده نشوند.
- برای احراز هویت NextAuth انتخاب شده است؛ Better Auth جایگزین آن نشود.
- اجزای مشترک در components و منطق مشترک در lib یا hooks قرار می‌گیرند. ساختار و مسئولیت‌ها در ARCHITECTURE.md توضیح داده شده‌اند.
- مستندات موضوعی در md نگه‌داری شوند؛ فایل مستند جدا برای هر کامپوننت ساخته نشود.

## بررسی تغییرات

برای تغییرات کد، بررسی متناسب با دامنه اجرا شود. پیش از آماده‌کردن مجموعه تغییرات برای کامیت، دستورهای زیر بررسی کامل فعلی پروژه‌اند:

```bash
npm run check
npm run build
```

Vitest سبک با محیط Node، یک worker و بدون موازی‌سازی فایل‌ها تنظیم شده است. تست‌ها در tests قرار دارند و تم، bootstrap، رنگ و کنتراست، ترجمه‌ها، اعتبارسنجی و هش رمز، ثبت‌نام، callbackهای نشست و مجوز نقش‌ها را پوشش می‌دهند. آخرین نتیجهٔ جاری در [بررسی پنل مدیریت](#بررسی-پنل-مدیریت) ثبت شده است؛ گزارش‌های تاریخ‌دار پایین این سند نتایج همان تاریخ‌اند. آزمون یکپارچه ورود جداگانه با auth:check اجرا می‌شود؛ جریان خرید هنوز پیاده‌سازی و تست نشده است.

برای تغییرات ظاهری و انیمیشن، بررسی واقعی مرورگر لازم است. حالت اولیه، حین حرکت، پایان حرکت، تعامل تکراری و مسیر اصلی دکمه بررسی شوند. در تعویض محصول چند بار بین هر سه محصول جابه‌جا شوید. برای تغییر responsive، عرض‌های مرتبط و اسکرول افقی بررسی شوند. بررسی مرورگر جای تست روی گوشی فیزیکی یا audit جامع دسترس‌پذیری را نمی‌گیرد.

Playwright، axe، jsdom و CI چندمرحله‌ای در وابستگی‌های پایه اضافه نشده‌اند. تست مرورگری خودکار باید هنگام پیاده‌سازی مسیرهای ضروری ورود یا خرید، بر اساس همان رفتار واقعی اضافه شود.

### بررسی تنظیمات رنگ‌بندی

آخرین بررسی ۲۰۲۶/۱۱/۲۰: `npm run check` با ۹۶ تست در ۱۲ فایل موفق بود و lint، TypeScript، Vitest و قالب‌بندی را شامل شد. آخرین بیلد Webpack پس از اصلاح چیدمان و حالت بارگذاری موفق بود؛ پس از تغییرات نهایی هاور، ترجمه و دکمهٔ بازگشت، check اجرا شد و بیلد تازه‌ای برای این سه تغییر اجرا نشده است.

شش migration در پروژه وجود دارند؛ migration ششم روی دیتابیس اعمال شد و دو تم ثابت برند را از آرایهٔ چهار انتخاب مدیر جدا کرد. تست‌ها مجوز ADMIN/OWNER، رد مهمان و مشتری، الزام چهار نام رسمی متفاوت، رد TechLight/TechDark در ارسال مدیر، شکست ذخیره، تطبیق فهرست با daisyUI، بازیابی brand/custom، اعتبارسنجی رنگ، حالت سیستم، bootstrap و storage خراب/مسدود را پوشش می‌دهند.

بررسی مرورگر این رفتارها را تأیید کرد:

- شش گزینهٔ کاربر با تم اصلی ثابت در ابتدا، چهار تم مدیر و رنگ دلخواه در انتها؛ تغییر رنگ فوری، حفظ پس از reload و بازنشانی رنگ‌های برند.
- انتخاب مستقیم چهار کارت، جایگزینی قدیمی‌ترین انتخاب با کلیک پنجم، چند انتخاب پیاپی و حفظ ترتیب پس از ذخیره. انتخاب‌های آزمایشی به آرایه و ترتیب اولیه بازگردانده شدند.
- شش ستون در دسکتاپ و نبود اسکرول داخلی شبکه؛ در رفت‌وبرگشت کاربران و رنگ‌بندی، موقعیت افقی سایدبار/محتوا و scrollY ابتدای صفحه ثابت ماندند.
- opacity منتخب‌ها ۱ و سایر کارت‌ها ۰٫۶؛ هاور واقعی به ۱ و خروج ماوس به ۰٫۶ با مدت ۰٫۲۵ ثانیه، در حالت روشن و تیره.
- فیلتر و تعداد کنار divider، شمارندهٔ لاتین `04/04`، نبود جست‌وجو و پیام موفقیت در صفحهٔ رنگ‌بندی، و نمایش ترجمه‌ها در فارسی/انگلیسی.
- دکمهٔ «تم اصلی سایت» هر دو TechLight و TechDark را فعال کرد؛ آرایهٔ چهار انتخاب قبل و بعد یکسان بود.

تست بصری موبایل، ورود مستقل ADMIN و شبیه‌سازی قطع شبکه در مرورگر انجام نشدند؛ مجوز و شکست ذخیره تست سروری دارند. این گزارش جای audit کامل دسترس‌پذیری یا آزمون روی گوشی واقعی نیست. جزئیات رفتار جاری در [سیستم طراحی](DESIGN_SYSTEM.md#تم-و-رنگ) و [معماری](ARCHITECTURE.md#ناوبری-و-پوسته) هستند.

پس از تغییر schema، کلاینت Prisma قدیمی در حافظهٔ dev معتبر نیست؛ getDb نسخهٔ جاری schema را برای بازسازی کلاینت بررسی می‌کند.

### بررسی پنل مدیریت

#### وضعیت نهایی رابط در ۲۰۲۶/۱۱/۲۰

سایدبار ساختار درختی دارد. «تنظیمات» کنترل بومی details/summary است و با کلیک یا Enter/Space باز و بسته می‌شود؛ فقط فرزند «رنگ‌بندی» لینک است. صفحهٔ مستقل SettingsOverview حذف شده و ورود به `/[locale]/admin/settings` به رنگ‌بندی هدایت می‌شود. گروه مسیر فعال باز می‌شود. در موبایل، کنترل والد کشو را باز نگه می‌دارد و انتخاب فرزند آن را می‌بندد. فاصلهٔ نهایی والد تا زیرمنو ۸ پیکسل است؛ در مرورگر در فارسی روشن و انگلیسی تیره اندازه‌گیری شد. رفتار حالت جمع‌شده و tooltipها نیز بررسی شد.

تیتر و زیرتیتر در layout ثابت کاربران و رنگ‌بندی و قاب مشترک AdminPageFrame قرار دارند. انیمیشن اصلی هنگام ورود اجرا می‌شود، ولی تعویض اسکلتون با داده و تغییر مرتب‌سازی آن را دوباره شروع نمی‌کند. فریم‌های بارگذاری و داده، ادامهٔ حرکت و ثابت‌ماندن مختصات قاب تیتر را نشان دادند؛ پس از پایان ورود، مرتب‌سازی transform تازه‌ای روی تیتر ایجاد نکرد. قاب جدول از حداقل `min(70dvh, 30rem)` استفاده می‌کند؛ در اندازهٔ بررسی‌شده ارتفاع نهایی ۴۸۰ پیکسل بود. عدد ۴۶۴ پیکسل مربوط به نسخهٔ قبلی این قاب بود و مقدار جاری نیست. ردیف جست‌وجوی نوار بالا فضای خود را هنگام رفتن به رنگ‌بندی حفظ می‌کند. قواعد جاری در [پنل مدیریت](DESIGN_SYSTEM.md#پنل-مدیریت) و مسئولیت layout در [ناوبری و پوسته](ARCHITECTURE.md#ناوبری-و-پوسته) ثبت شده‌اند.

آواتار بدون عکس در نوار پنل با حساب واردشده بررسی شد. پس‌زمینهٔ گرادیانی مستقیماً از متغیرهای رنگ تم استفاده می‌کند. حرف یا آیکون وسط آن span مستقل با گذار رنگ محلی یک‌ثانیه‌ای دارد. آزمایش حذف این گذار، هم‌زمانی رنگ حرف و ریشه را نشان داد، اما کاربر رفتار قبلی را ترجیح داد و گذار مستقل بازگردانده شد؛ بنابراین گزارش آزمایش همگام‌سازی، وضعیت نهایی پیاده‌سازی نیست. نمونه‌های میانی رنگ حرف و پس‌زمینه جداگانه بررسی شدند؛ بررسی قدیمی آواتار جدول به‌تنهایی تأیید آواتار نوار پنل یا رنگ حرف آن نبود.

#### دامنهٔ اعتبارسنجی تغییرات اخیر

آخرین اجرای کامل بررسی کد، `npm run check` با ۹۶ تست در ۱۲ فایل بود و lint، TypeScript، Vitest و قالب‌بندی را شامل شد. بیلد `npm run build -- --webpack` پس از تغییر منطق گروه‌ها و هدایت مسیر تنظیمات موفق شد. اصلاح نهایی جای فلش گروه، فاصلهٔ ۸ پیکسلی و قالب‌بندی پس از آن بیلد انجام شدند؛ برای این اصلاحات بیلد تازه اجرا نشد. اصلاح فاصله در مرورگر و با Prettier بررسی شد. در این به‌روزرسانی مستندات نیز تست برنامه یا بیلد تازه اجرا نشده است.

بررسی مرورگر شامل دسکتاپ، عرض ۳۹۰، فارسی/انگلیسی، روشن/تیره، بازوبسته‌شدن گروه، کیبورد، ناوبری فرزند، هدایت آدرس قدیمی و حالت جمع‌شده بود. در بررسی رنگ‌ها فقط ترجیح محلی مرورگر تغییر کرد؛ انتخاب‌های ذخیره‌شدهٔ مدیر و اطلاعات حساب‌ها تغییر نکردند. گوشی فیزیکی، سنجش آزمایشگاهی CLS و شبیه‌سازی reduced-motion در این نوبت بررسی نشدند.

#### بررسی اولیهٔ مدیریت کاربران

بررسی ۲۰۲۶/۱۱/۲۰: `npm run lint`، `npm run typecheck` و `npm test` موفق بودند؛ Vitest تعداد ۶۸ تست در ۱۱ فایل را گزارش کرد. قالب‌بندی فایل‌های تغییرکرده با Prettier بررسی شد. برای این تغییرات بیلد تولیدی تازه یا آزمون یکپارچهٔ کامل دیتابیس اجرا نشده است؛ نتیجهٔ قدیمی Webpack به‌معنی بیلد تازه نیست.

تست‌های پنل مجوز عملیات، حفاظت مالک، کنترل نسخهٔ درخواست، حذف کاربر/مدیر، حفظ سفارش هنگام رد حذف، استقلال تغییر نقش و وضعیت، مرتب‌سازی پیش از صفحه‌بندی و حذف ایمیل مدیر/مالک از دادهٔ بینندهٔ ADMIN را با دیتابیس mock بررسی می‌کنند. تست ورود، پیام حساب غیرفعال را فقط بعد از رمز صحیح و حفظ خطای عمومی برای رمز اشتباه پوشش می‌دهد.

در مرورگر داخلی، ظاهر جدول و مودال‌های شیشه‌ای، تاریخ عددی، ردیف حساب جاری، آیکون‌ها و تولتیپ‌ها، مرتب‌سازی نقش و وضعیت در هر دو جهت، حفظ مرتب‌سازی همراه فیلتر، و انصراف از عملیات بررسی شدند. بررسی ظاهر شامل فارسی/انگلیسی، روشن/تیره و عرض موبایل ۳۹۰ بود. حفظ سایدبار جمع‌شده پس از تغییر زبان و ناوبری نیز بررسی شد. برای بررسی حذف، حساب واقعی حذف نشده و نتیجهٔ حذف از تست‌های mock است. محدودیت نمایش ایمیل ADMIN با تست سروری بررسی شده، نه با ورود جداگانه به حساب مدیر در مرورگر. در بازنگری ۲۰۲۶/۱۱/۲۰، جدول اسکرولی موبایل با table-pin-cols در هر دو جهت بررسی شد: پس از حدود ۳۹۹ پیکسل اسکرول افقی، ستون اول جابه‌جا نشد. حذف divider موبایل، دکمهٔ soft-error پاک‌کردن فیلتر و حفظ مرتب‌سازی، آیکون primary سرستون و آیکون soft هم‌رنگ پیش از تیتر مودال نیز بررسی شدند. تراز دکمه‌های مودال در انگلیسی راست و در فارسی چپ است.

در بازنگری موبایل ۲۰۲۶/۱۱/۲۰، جمع‌شدن ستون کاربر از ۱۷۶ به ۷۲ پیکسل پس از اسکرول افقی و بازگشت به عرض اولیه در ابتدای جدول بررسی شد. نام و ایمیل در حالت باز تک‌خطی با سه‌نقطه‌اند؛ در حالت جمع‌شده فقط آواتار دیده می‌شود. هاور انصراف نیز در فارسی/انگلیسی و روشن/تیره بررسی شد. اجرای کامل `npm run check` موفق بود و شامل قالب‌بندی کل پروژه و همان ۶۸ تست است.

همچنین پس از انتقال خواندن نشست به مرز درخواست، بارگذاری مجدد پنل بدون خطای پیش‌رندر مقدار تصادفی NextAuth بررسی شد. قرارداد این مرز در [معماری](ARCHITECTURE.md#احراز-هویت) ثبت شده است.

## اتصال دیتابیس

پروژه موجود Supabase با نام tech-shop در Frankfurt استفاده می‌شود؛ پروژه جدید نسازید. فایل `.env.example` را به `.env.local` کپی و رمز percent-encoded را فقط در فایل محلی وارد کنید. تمام فایل‌های env به‌جز نمونه بدون رمز در Git نادیده گرفته می‌شوند. متغیر اتصال نباید پیشوند NEXT_PUBLIC_ داشته باشد.

`DATABASE_URL` برای برنامه و `DIRECT_URL` اختیاری برای Prisma CLI است؛ در نبود DIRECT_URL، CLI از DATABASE_URL استفاده می‌کند. اتصال فعلی Session pooler روی پورت 5432 است، چون مسیر مستقیم به IPv6 نیاز دارد. برای هر دو URL از `sslmode=verify-full` استفاده کنید. گواهی نامعتبر را با غیرفعال‌کردن TLS دور نزنید؛ در صورت نیاز CA رسمی را با `sslrootcert` مشخص کنید. Next.js، CLI و اسکریپت تست، env را با همان ترتیب استاندارد Next.js می‌خوانند.

```bash
npm run db:generate
npm run db:validate
npm run db:check
npm run db:migrate:status
```

برای آزمون یکپارچه احراز هویت، سرور محلی با NEXTAUTH_URL مطابق همان مبدأ اجرا شود و سپس `npm run auth:check` اجرا شود. مبدأ پیش‌فرض آزمون `http://localhost:3100` است و با AUTH_TEST_URL قابل تغییر است؛ فقط localhost یا 127.0.0.1 پذیرفته می‌شود. آزمون یک کاربر CUSTOMER با ایمیل تصادفی example.invalid می‌سازد و در پایان همان کاربر و bucketهای اختصاصی‌اش را پاک می‌کند. secret، cookie یا رمز آزمایشی در خروجی چاپ نمی‌شود. این دستور opt-in است و عضو check روزمره نیست، چون دیتابیس واقعی را برای داده آزمایشی می‌نویسد. اجرای پشت‌سرهم همچنان زیر محدودیت سراسری ورود قرار می‌گیرد.

`db:check` همان ماژول سروری برنامه را بارگذاری می‌کند و SELECT 1 واقعی را با Prisma/pg اجرا می‌کند؛ خطای خام در خروجی چاپ نمی‌شود. این اسکریپت با شرط react-server اجرا می‌شود تا مرز server-only در محیط Node قابل استفاده باشد. endpoint عمومی تشخیص دیتابیس وجود ندارد. build و typecheck پیش از اجرا client را تولید می‌کنند؛ تولید کد به رمز یا شبکه دیتابیس نیاز ندارد.

گواهی عمومی `certs/supabase-prod-ca-2021.crt` از [مخزن دانلود رسمی Supabase](https://supabase-downloads.s3.ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt) دریافت شده است و secret نیست. URL برنامه آن را با sslrootcert بارگذاری می‌کند؛ مسیر باید روی میزبان موجود باشد. تنظیم CLI مسیر را مطلق و گزینه‌های TLS را به sslcert و sslaccept=strict تبدیل می‌کند تا schema engine نیز CA و نام میزبان را بررسی کند. CA با fingerprint SHA-256 برابر `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA` تا ۲۰۳۱/۰۴/۲۶ معتبر است؛ پیش از انقضا یا تعویض گواهی سرور بازبینی شود.

schema اکنون ۱۲ مدل اولیه فروشگاه و NextAuth دارد. هر سه migration در ۲۰۲۶/۱۱/۰۶ با تأیید مالک روی پروژه موجود Supabase اعمال شدند. Prisma migrate status وضعیت up to date و migrate diff از دیتابیس به schema وضعیت No difference detected را گزارش کرد. index یکتایی OWNER و trigger حفاظت آن در دیتابیس وجود دارند و trigger فعال است. schemaهای auth و storage متعلق به Supabase هستند و تغییر نکرده‌اند. db push/reset روی این پروژه اجرا نشود؛ migrate dev باید دیتابیس توسعه و shadow مستقل داشته باشد.

برای NextAuth، NEXTAUTH_SECRET تصادفی با دست‌کم ۳۲ نویسه و NEXTAUTH_URL برابر مبدأ کامل برنامه در env خصوصی لازم‌اند. secret محلی بدون چاپ تولید شده است؛ در استقرار عمومی آن را از secret manager بگیرید و NEXTAUTH_URL را به دامنه HTTPS تغییر دهید. در اجرای آزمایشی روی پورت دیگر، متغیر را فقط برای همان فرایند override کنید تا کنترل Origin ثبت‌نام درست بماند.

بررسی نهایی ۲۰۲۶/۱۱/۰۶: npm run check با ۴۴ تست و بیلد Webpack موفق بودند. دستور npm run auth:check با سرور تولیدی محلی و Supabase واقعی، رد مهمان، Origin نامعتبر، رمز ۷ نویسه، پذیرش رمز ۸ نویسه، هش رمز، نادیده‌گرفتن نقش OWNER ورودی، جلوگیری از بازنویسی رمز و نقش با ثبت‌نام تکراری، رد رمز اشتباه، ورود صحیح، حفظ نشست، دسترسی محافظت‌شده، خروج، ابطال با sessionVersion و محدودیت تلاش ورود را تأیید کرد. در مرورگر هم ثبت‌نام، خطای رمز اشتباه، ورود، ماندگاری نشست پس از reload و خروج تأیید شدند. حساب‌ها و شمارنده‌های اختصاصی آزمون پاک شدند و شمارش حساب‌های آزمایشی باقی‌مانده صفر بود.

محدودیت بیلد قبلاً تأییدشده: npm run build در Turbopack با خطای داخلی خروج worker پردازش CSS پیش از برقراری اتصال شکست خورد و خارج از sandbox نیز تکرار شد. بیلد تازه با npm run build -- --webpack موفق بود؛ موتور پیش‌فرض تغییر نکرد. خطای TLS اتصال با CA رسمی برطرف شده است و تست Prisma / PostgreSQL موفق است.

## بررسی نقش مالک

حساب OWNER در ۲۰۲۶/۱۱/۰۶ با اطلاعات خصوصی env محلی ساخته شد؛ دقیقاً یک مالک، فعال‌بودن حساب، تطابق hash و ورود/خروج واقعی با نقش نشست OWNER روی پورت‌های ۳۰۰۰ و ۳۱۰۰ تأیید شدند. هیچ ایمیل یا رمزی در خروجی یا مستندات ثبت نشده است.

برای provisioning خارج از برنامه، OWNER_EMAIL و OWNER_PASSWORD را فقط در env محلی تنظیم و `npm run owner:provision -- --check` و سپس `npm run owner:provision` اجرا کنید. اسکریپت مالک دوم یا بازنویسی رمز را مجاز نمی‌کند. اگر ایمیل از قبل حساب دارد، باید رمز همان حساب تطابق داشته باشد و حساب فعال باشد؛ ارتقای آن sessionVersion را افزایش می‌دهد. اجرای مجدد برای همان مالک صرفاً اعتبارسنجی است. پس از تغییر schema و تولید مجدد Prisma، سرور توسعه را راه‌اندازی مجدد کنید تا client ذخیره‌شده در global با schema قبلی باقی نماند.

در ۲۰۲۶/۱۱/۰۶ دو migration `20261106123211_add_owner_role` و `20261106123212_protect_single_owner` آماده شدند؛ migration اولیه قبلی بازنویسی نشد. همه migrationها روی PostgreSQL موقت محلی با PGlite 0.5.15 اعمال شدند. ساخت یک OWNER و دو ADMIN موفق، ساخت/ارتقای مالک دوم با 23505 رد، حذف/تنزل/تغییر ایمیل و رمز/غیرفعال‌سازی مالک با 42501 رد، افزایش sessionVersion مالک و حذف CUSTOMER موفق بودند. این آزمایش روی Supabase اجرا نشده است.

npm run check با ۴۴ تست موفق، تلاش ثبت‌نام با نقش ADMIN و OWNER، تازه‌سازی نقش قدیمی OWNER از DB و قواعد مجوز تغییر نقش را پوشش داد. ابزار تست موقت فقط در .taste-skill نصب شد؛ وابستگی پایه پروژه تغییر نکرد. migrationهای مالک اکنون روی Supabase اعمال و وجود index و فعال‌بودن trigger تأیید شده‌اند. حساب OWNER واقعی اکنون با اطلاعات env خصوصی و خارج از مسیر عمومی ساخته شده است.

## امنیت وابستگی‌ها

گزارش تاریخ‌دار وابستگی‌های توسعه در [SECURITY.md](SECURITY.md) است. نتیجه قدیمی audit به‌عنوان نتیجه اجرای تازه گزارش نشود. ارتقای ابزار نصب کامپوننت یا تغییر registry باید با محدوده سازگاری و بررسی ورودی همراه باشد. ابزار shadcn فعلاً نصب است؛ رابط فعلی از daisyUI استفاده می‌کند.

## بررسی نسخه انگلیسی

در ۲۰۲۶/۱۱/۰۵، `npm run check` با ۲۴ تست و `npm run build` موفق شدند. نسخه تولیدی انگلیسی در مرورگر در عرض‌های ۳۹۰ و ۱۴۴۰ بررسی شد: رفت‌وبرگشت زبان، جهت سند، منوی موبایل، نتایج دسته‌بندی و جست‌وجو، تنظیم تم و معرفی محصول. تعویض تکراری هر سه محصول و فریم‌های میانی بررسی شدند؛ در عرض ۳۹۰ اسکرول افقی مشاهده نشد. آزمایش روی گوشی فیزیکی انجام نشده است.

در بازنگری تغییر زبان، تم تیره navy و پالت cobalt هنگام رفت‌وبرگشت فارسی/انگلیسی حفظ شدند؛ حالت روشن، Back مرورگر، تعویض تکراری هر سه محصول و فریم‌های میانی RTL/LTR در عرض ۳۹۰ نیز بررسی شدند. تغییر زبان بدون بارگذاری مجدد و با حفظ محصول انتخابی انجام می‌شود.

پس از جایگزینی fade با حرکت چیدمان، فریم میانی تغییر زبان در مرورگر با opacity بدنه برابر ۱ و transform فعال روی متن و محصول بررسی شد. رفت‌وبرگشت زبان، تعویض محصولات پس از آن و عرض موبایل ۳۹۰ بررسی شدند؛ lint، TypeScript، ۲۴ تست و بیلد موفق بودند.

## کنترل متن‌های رابط

پیش از افزودن متن قابل نمایش، کلید معنادار آن را در هر دو کاتالوگ ترجمه تعریف کنید و در کامپوننت از useTranslations بخوانید. برای جمله‌های دارای متغیر از پارامترهای ICU استفاده کنید؛ جمله را در JSX به قطعه‌های زبانی مستقل نچسبانید. برچسب اجزای عمومی باید از محل استفاده ترجمه و پاس داده شود. قرارداد کامل در [معماری](ARCHITECTURE.md#مرز-متن-قابل-ترجمه) است.

تست `tests/ui-copy.test.ts` با AST کامپوننت‌ها و فایل‌های TSX برنامه را برای متن مستقیم JSX، literal در ویژگی‌های متنی، فیلدهای اطلاعات نمایشی و مقدار پیش‌فرض برچسب بررسی می‌کند. این تست تحلیل کامل جریان داده نیست؛ متن‌های محاسبه‌شده و داده سرویس‌های آینده همچنان نیاز به بازبینی دارند. تست کاتالوگ‌ها نیز برابری کلیدهای تو‌در‌تو، متن غیرخالی، زبان انگلیسی و تطابق پارامترها را بررسی می‌کند.

بررسی ۲۰۲۶/۱۱/۰۵: نام لاتین سه محصول، برچسب پیش‌فرض لوگو و عنوان تب به کاتالوگ منتقل شدند؛ قالب برچسب رنگ‌ها و نشانه‌های متنی هم از کاتالوگ خوانده می‌شوند. `npm run check` با ۲۶ تست موفق و `npm run build` تأیید شدند.

### تست هم‌زمان زبان و تم

در ۲۰۲۶/۱۱/۰۵، گذار تم به ۱۰۰۰ میلی‌ثانیه تغییر کرد. در مرورگر تولیدی، ۶ تغییر ترکیبی زبان/تم در دسکتاپ، ۶ تغییر سریع پشت‌سرهم حالت و ۴ تغییر ترکیبی در عرض ۳۹۰ بررسی شدند. نمونه‌برداری میانی transitionDuration برابر 1s، رنگ‌های میانی متفاوت و localeMoving فعال را هم‌زمان نشان داد. در پایان data-theme-changing و data-locale-moving پاک شدند، حالت checkbox با تم نهایی تطابق داشت، اسکرول افقی موبایل وجود نداشت و خطای کنسول مشاهده نشد. این نتیجه محدود به مرورگر بررسی‌شده است؛ آزمون گوشی فیزیکی یا شبیه‌سازی reduced-motion انجام نشد.

## ایمیل بازیابی رمز

برای تحویل ایمیل، `RESEND_API_KEY` و `RECOVERY_EMAIL_FROM` را در env خصوصی تنظیم کنید. نشانی فرستنده باید روی دامنهٔ تأییدشده در Resend باشد. پیوند بازیابی از `NEXTAUTH_URL` ساخته می‌شود. اگر هرکدام از این سه متغیر خالی باشد، گزینهٔ «فراموشی رمز عبور» در فرم ورود نمایش داده نمی‌شود.

## استفاده از صفحه‌بندی

برای فهرست‌های جدید از `components/pagination.tsx` استفاده کنید و منطق بازهٔ شماره‌ها را در صفحه تکرار نکنید. نام ورودی‌ها و قواعد ظاهر در [مرجع صفحه‌بندی مشترک](DESIGN_SYSTEM.md#صفحه‌بندی-مشترک) ثبت شده‌اند. تست منطق بازه‌ها در `tests/pagination.test.ts` است. تغییرات مرورگر در هر دو زبان و تم و عرض موبایل بررسی شوند.

بررسی skeleton در ۲۰۲۶/۱۱/۲۰: `npm run check` با ۶۸ تست موفق بود. اجزای بارگذاری حساب و کاربران در مسیر پیش‌نمایش موقت، در مرورگر با فارسی/انگلیسی و تم روشن/تیره بررسی شدند؛ مسیر موقت پس از بررسی حذف شد. این بررسی ظاهر اجزا است؛ کندسازی شبکه و آزمون کامل نشست و ناوبری پنل در این نوبت اجرا نشده‌اند.

نوار بالای پنل نیز هنگام خواندن اولیهٔ نشست، جای نام و آواتار skeleton نشان می‌دهد. بیلد تولیدی Webpack پس از افزودن مرزهای بارگذاری با موفقیت انجام شد.

### سوییچ تست skeleton در توسعه

در `npm run dev` دکمهٔ ثابت پایین صفحه «تست اسکلتون (dev)» نمایش داده می‌شود. با کلیک، بخش حساب، آیکون حساب هدر، نام و آواتار نوار پنل و فهرست کاربران به skeleton تبدیل می‌شوند؛ «نمایش محتوا (dev)» آن‌ها را برمی‌گرداند. این سوییچ فقط نمایش را تغییر می‌دهد و درخواست یا کنترل دسترسی سرور را دور نمی‌زند. وضعیت در حافظه است و با refresh خاموش می‌شود. در production، provider تست نصب نمی‌شود و hook همیشه false برمی‌گرداند؛ دکمه یا پارامتر URL برای فعال‌کردن آن وجود ندارد.

بررسی سوییچ توسعه در ۲۰۲۶/۱۱/۲۰: `npm run check` با ۶۸ تست موفق شد. سوییچ حساب در هر دو زبان و تم و برگشت از skeleton به محتوای واقعی بررسی شد؛ فهرست کاربران و نوار حساب پنل نیز با سوییچ بررسی شدند. محل دکمه بالاتر از نشانگر Next.js قرار دارد تا روی هم نیفتند.

fallback اولیهٔ Suspense حساب هم از `AccountPageSkeleton` با قاب دو ستونه، ردیف تب‌ها و حداقل ارتفاع همان صفحه استفاده می‌کند. بررسی ۲۰۲۶/۱۱/۲۰: جابه‌جایی بین خلاصهٔ حساب و اسکلتون در مرورگر، فارسی/انگلیسی و روشن/تیره مقایسه شد؛ جای آواتار و ردیف‌ها با محتوای واقعی هماهنگ است. `npm run check` با ۶۸ تست موفق بود و پس از تکمیل قاب fallback و نام دسترس‌پذیر تب‌های غیرفعال، lint و typecheck دوباره موفق شدند. اندازه‌گیری آزمایشگاهی CLS انجام نشده است.

بررسی اسکلتون جدول کاربران در ۲۰۲۶/۱۱/۲۰: اسکلتون و دادهٔ واقعی از یک جدول نمایش داده شدند. اندازه‌گیری DOM در فارسی/انگلیسی دسکتاپ و عرض ۳۹۰ نشان داد عرض پنج ستون و ارتفاع چهار ردیف در سوییچ dev برابرند؛ در حالت جمع‌شدهٔ ستون موبایل نیز برابری حفظ شد (عرض ستون اول از ۱۷۶ به ۷۲ پیکسل). حالت روشن/تیره و RTL/LTR در مرورگر بررسی شدند. این مقایسه مربوط به دادهٔ موجود است و سنجش آزمایشگاهی CLS یا کندسازی شبکه نیست. `npm run check` با ۶۸ تست موفق شد.

بیلد تولیدی `npm run build -- --webpack` پس از یکپارچه‌سازی جدول و اسکلتون نیز موفق بود.

بررسی تصویر منتخب بدون عکس در ۲۰۲۶/۱۱/۲۴: طرح اول با متن `NO IMAGE` در فرم دسته‌بندی فارسی/انگلیسی و تم روشن/تیره بررسی شد. در جدول نیز دو ردیف بدون عکس با هر دو فایل روشن/تیره و بارگذاری موفق بررسی شدند؛ تغییر تم مسیر تصویر را عوض کرد. پس از افزودن فایل تیره، سرور توسعه دوباره اجرا شد تا فایل جدید در جدول نیز شناسایی شود. `npm run check` با ۱۳۶ تست در ۱۸ فایل و بیلد `npm run build -- --webpack` موفق بودند.
